# 멘토링 정리 (2026-10-20)

> 멘토링 자동 요약본을 바탕으로 정리했습니다. 요약에서 말이 불명확한 부분은 맨 아래 "원문이 불명확한 부분"에 따로 적었고, 본문에는 넣지 않았습니다.

## 1. 한눈에 보기

- 지난 멘토링에서 받은 두 가지(NPS 설문, 페르소나 시뮬레이션)를 했고, 방향이 맞다는 평가를 받았습니다.
- 페르소나 시뮬레이션은 API 호출만으로 했고, 50개 케이스면 충분하니 더 만들 필요는 없다고 했습니다.
- "양호"가 건강에 문제없다는 뜻으로 읽힐 수 있다는 발견은 설문으로 오해 비율을 먼저 재고, 결과에 따라 문구를 바꾸기로 했습니다.
- 건강정보 동의를 철회한 사용자가 공통 챌린지에 참여할 수 있는 문제가 확인됐고, 동의 여부를 확인하도록 고쳐야 합니다.
- 모델은 한 사이클 안에서 같은 모델로 비교해야 해서, 지금은 모델을 더 바꾸지 않기로 했습니다.
- 지인 테스트는 목요일에 합니다. 멘토 피드백 수정은 내일 하고, 다음 주 월요일에 설문 결과를 모읍니다.
- 문제를 발견하고 고친 과정 자체가 의미 있으니 발표 자료, 이력서, 포트폴리오에 넣으라고 했습니다(5번 참고).

## 3. 멘토 피드백

### 모델과 서비스 방향
- 모델 적용 결과가 긍정적이고, UI에 많은 고민이 담겨 퀄리티가 높다고 평가했습니다.
- 웹 서비스 개발은 잘 됐지만 모델에 대한 진지한 고민은 드물어 아쉽다고 했습니다.
- 지금은 영리 목적이 아닌 시범 운영이고, 서비스는 일주일 뒤 중단 예정이라는 점을 고려한 진행이라고 정리했습니다.
- 의료기기로 분류될 소지가 있어 실서비스 도입에는 신중해야 합니다. 의료기기로 취급되더라도 서비스를 진행하는 방안은 긍정적으로 검토했습니다.
- 사업화하려면 센서 부착이나 링 같은 기기와 연동하고, 의료기기 등록 계획을 구체적으로 세우는 것이 중요하다고 했습니다. 사업 관련 내용은 부트캠프 범위가 아니라 따로 논의해야 합니다.
- 의료 분야는 사이드로 하고 있고, 사업화한다면 커뮤니티형 리텐션 강화가 필요하다고 정리했습니다.

### 페르소나 시뮬레이션
- 화면 확인 없이 API 호출 순서만으로 돌린 것이고, 화면은 아직 안 봤다고 보고했습니다.
- 50개 케이스면 논문을 쓰기에 충분하니 케이스를 더 늘릴 필요는 없습니다.
- 중단 사용자는 기록이 남은 채 중단되는 문제가 확인돼서 수정하기로 했습니다(내일부터).

### "양호" 문구
- "양호"가 문제없음으로 오해될 수 있어서, 설문으로 사용자 이해를 정량으로 보기로 했습니다.
- 결과에 따라 면책 문구 추가 등 문구를 바꿉니다. 그 전에는 화면을 바꾸지 않습니다.

### 데이터 보관과 보안
- 사용자 접속 로그는 3개월, 업무 접속기록은 최소 2년으로 나눠 보관·파기하도록 했고, 통신비밀보호법 등 기준에 맞춰 기간과 파기 기준을 분명히 하라고 했습니다.
- DB 컬럼 중 이메일은 암호화 대상으로 권고합니다. 관리자 화면에서는 가려서 보여 주고, 필요할 때만 해제하는 방식을 제안했습니다.
- 건강 데이터는 민감정보라 암호화가 안전하지만, 시간이 부족하면 필수는 아닙니다. 못 했다면 암호화의 필요성은 알고 있다는 점을 문서에 분명히 적으라고 했습니다.
- 체험 안내 문서의 암호화 설명이 실제와 달라서, 디스크 암호화가 끝났음을 분명히 안내해야 합니다.
- API 약 100개를 10개씩 그룹으로 나눠 보안 검사하고, 회원가입 API 그룹은 특히 꼼꼼히 봅니다. 크리티컬한 결과만 골라 발표 자료로 씁니다.
- AWS는 한 사람의 계정으로 쓰지 말고 멤버별 IAM 계정을 만들어 개별 로그인하게 해야 합니다.

### 모델 변경
- 12주 챌린지 한 사이클 안에서는 4주 전, 현재, 4주 후를 같은 모델로 분석해 비교해야 합니다.
- 중간에 모델을 바꾸면 피처가 달라져 비교가 안 되므로, 지금은 모델을 바꾸지 않고 진행합니다.
- 중간에 새로 들어온 사용자의 데이터는 따로 분석하도록 코드에서 미리 나눠야 합니다.
- 모델을 바꾸게 될 때는 1.0에서 2.0으로 넘어가는 경우를 가정해 미리 준비하는 방식을 권합니다.

### 동의와 인증
- 공통 챌린지는 로그인만으로 참여하지 못하게 하고, 건강정보 동의 여부를 확인해야 합니다.
- 건강정보 동의를 철회하면 인증이 풀려 다시 로그인해야 하고, 그 과정에서 재참여와 공통 챌린지 입력이 안 되는 문제가 나왔습니다. 요약에는 "토큰에 건강정보가 들어 있어서"라는 추정이 적혀 있습니다(확인 필요: 6번).

### 지인 테스트
- 길게 하지 않고 짧은 기간에 빠르게 합니다. 가상 데이터를 미리 넣어 두는 방안도 나왔습니다.
- 실생활에서는 4주가 걸리는 설문을, 1시간 안에 4주치 데이터를 넣거나 28일 중 25일치를 미리 넣고 3일치만 체험하게 하는 식으로 줄일 수 있습니다.
- 시연 도구는 화면에서 날짜를 하루씩 옮길 수 있습니다.
- 피드백을 받아 고치는 반복(피드백 루프)을 돌리는 과정이 중요합니다.

### 일반 조언
- 이력서와 포트폴리오를 강조하는 이유는 부트캠프의 목표가 취업이기 때문입니다.
- 개발자 구분이 백엔드, 프론트엔드, AI로 나뉘어도 서로 영향을 주는 문제는 먼저 공유하는 것이 좋습니다.
- AI는 문제를 정의하고 핵심을 찾는 일은 아직 약하고, 정해진 과제를 실행하는 데 강합니다. 사람은 규칙, 우선순위, 포함·제외를 정하고 결과를 검토합니다.

## 5. 발표·이력서·포트폴리오에 넣을 사례 후보

멘토님이 "흐름을 이렇게 고쳤다"는 과정을 넣으라고 한 네 가지입니다. 수정이 끝난 뒤 근거를 채웁니다.

| 후보 | 설명할 흐름 | 남길 근거 |
|---|---|---|
| 동의 철회 후 재수집 차단 | 기존 테스트 통과 뒤 재입력이 허용되는 문제 발견 → 동의 검사 적용 → 재입력 거부 확인 | 철회 전후 요청 결과, 수정 커밋, 회귀 시험 |
| 모델 교체 후 과거 결과 보존 | 버전 저장만으로 설명 보존이 안 됨 → 당시 해석 보존, 비교 제한 안내 | 구버전·신버전 결과 화면, 교체·복구 검사 |
| 암호화와 복구 | 보호할 정보 선정 → 기존 데이터 변환 → 로그인·분석·복원 확인 | 민감도에 따른 선택 근거, 비밀값 없는 절차·검사 결과 |
| 사용자 흐름 개선 | 처음 온 사람이 막힌 단계 관찰 → 화면 수정 → 같은 과제 재확인 | 관찰 인원·상황, 전후 화면, 도움 없이 완료한 사례 |

"양호" 오해 사례도 같은 방식입니다. 오해 가능성을 발견하고, 설문으로 정량 확인한 뒤, 결과에 따라 문구를 바꾸는 과정을 근거와 함께 남깁니다.

## 6. 우리 쪽에서 확인할 것

- 요약의 "토큰에 건강정보가 있다"는 추정은 로컬에서 로그인 토큰을 풀어 본 결과와 다릅니다. 토큰에는 사용자 번호, 종류, 발급·만료 시각, 세션 번호만 있었습니다. 철회 때 세션이 폐기되는 것이 원인인지 서버 코드로 확정해야 합니다.
- 공통 챌린지 외에 커뮤니티·파이·캐릭터도 동의 철회 때 막을지 정해야 합니다.
- 이전 모델(v0.1.1)로 분석한 실사용자가 있는지 확인해야 합니다. 지인 테스트 사용자는 모두 v0.2.0이라 영향이 없을 수 있습니다.
- 체험 종료일과 삭제일, 처리방침 시행일을 정해야 합니다.

## 원문이 불명확한 부분

요약본에 말이 맞지 않는 곳이 있어서 본문에 넣지 않았습니다. 정확한 내용을 아는 분이 채워 주세요.

- "연체 관련 내용을 정리하는 것이 바람직하다" (연체가 무엇을 가리키는지 불명확)
- "기록 종류 중 상위 3가지만 참고해 9분 단위로 기간 설정" (9분이라는 단위)
- "이메일, 청약, 월요일 관련 정보는 필수 암호화 대상" (청약·월요일이 무엇인지 불명확)
- "예산 투입 후 큰 문제는 없었던 것으로" (문맥상 시뮬레이션 결과를 말하는 것으로 보임)
- "GN 테스트", "GA 테스트" (지인 테스트를 말하는 것으로 보임)
- "서버 로그 자료는 터치티피와 연동해 찾은 내용을 디스코드에 캡처로 공유" (터치티피가 무엇인지 불명확)
- "오후라 링" (센서 기기를 말하는 것으로 보임)
