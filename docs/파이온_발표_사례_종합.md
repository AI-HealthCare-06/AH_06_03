## 사례 1. 건강정보 동의 철회 후 재수집 차단

> 담당: 이슬(철회 API 첫 구현·화면·문구·푸시 구독 정리), 혜림·효민(서버 차단 확대)

---

### 슬라이드용 한 장

**제목:** 시험이 모두 통과해도 빠져 있던 곳 — 철회한 사람의 데이터가 다시 쌓이는 경로 차단

| 항목 | 내용 |
|---|---|
| 문제 | 시험은 모두 통과했는데, 멘토링에서 "철회해도 로그인은 유지된다"는 지적이 나왔어요. 같은 토큰으로 철회 상태를 재현하니 **공통 챌린지 참여·인증이 201(저장됨), 커뮤니티·파이·캐릭터가 200(이용됨)** 이었어요 |
| 선택 | 철회하면 **기능 묶음 전체를 차단**(403 CONSENT_WITHDRAWN) |
| 선택한 이유 | 처음에는 참여·인증만 막는 안(A)으로 구현했는데, 목록은 그대로 보여 약관("철회 시 이용 불가")과 어긋나고 새 기능이 생기면 또 빠질 수 있었어요. 그래서 묶음 전체 차단(B)으로 바꿨어요 |
| 제약사항 | 계정 정보, 다시 동의, 현재 약관, 내려받기, 탈퇴는 철회 뒤에도 열어 둬야 해요(복귀·권리 행사 경로) |
| 수정 전 → 후 | 공통 챌린지 201 → 403, 커뮤니티·파이·캐릭터 200 → 403 |
| 재확인 | 막혀야 할 7곳은 403, 열려야 할 4곳은 200인 회귀 시험 추가, 전체 시험 330개 통과 |

**한 줄 결론:** "시험이 모두 통과한다"는 시험이 다룬 경로가 안전하다는 뜻일 뿐이라서, 상태가 바뀌는 경로(철회 뒤 로그인 유지)를 시험 데이터로 직접 만들어 검사해야 빈틈이 드러나요.

---

### 1. 문제 발견

- 기존 시험은 모두 통과했어요.
- 멘토링에서 "철회해도 로그인은 유지된다"는 지적이 나왔고, 같은 토큰으로 철회 상태를 재현해 봤어요.
- 결과: 공통 챌린지 참여·인증이 **201(저장됨)**, 커뮤니티·파이·캐릭터가 **200(이용됨)**.

### 2. 원인과 판단

- 동의 검사를 기능 묶음마다 붙이는 방식이라, 나중에 추가된 묶음에서 빠졌어요.
- 시험이 "철회 기록이 있는 회원"을 다루지 않아서 못 잡았어요.
- 약관("철회 시 이용 불가")에 맞춰 **묶음 전체 차단**으로 정했어요.

**선택지 비교**: 처음에는 "참여·인증만 차단"(A)으로 구현했어요. 목록은 보이지만 약관과 어긋나고, 새 기능이 생기면 또 빠질 수 있었어요. 팀 결정을 확인한 뒤 **묶음 전체 차단**(B)으로 바꿨고, A 커밋은 `git revert`로 기록을 남겼어요(14c8632 → b018087).

### 3. 수정

- 커뮤니티·파이·캐릭터에 공통 동의 검사를 붙이고 응답을 **403 CONSENT_WITHDRAWN**으로 통일했어요.
- 계정, 다시 동의, 내려받기, 탈퇴는 열어 뒀어요.
- 푸시는 철회 시 구독을 삭제하고 알림을 멈췄어요.
- 이슬 몫: 막혔을 때 안내 배너와 마이페이지 링크, 철회할 때 이 브라우저의 알림 구독 해제.

| 날짜 | 한 일 |
|---|---|
| 10/8 | 철회 API 첫 구현, 철회 상태에서 건강정보 API가 403(742d137), 마이페이지 철회·다시 동의 연결과 안내 배너(3bba955) |
| 10/13~10/20 | 문구 정리: 철회하면 건강정보가 삭제된다, 철회하면 서비스를 이용할 수 없다 |
| 10/21 | 서버 차단 확대(혜림·효민): 커뮤니티·파이·캐릭터·공통 챌린지(PR #149) |
| 10/23 | 철회해도 브라우저에 남던 푸시 구독을 철회할 때 해제(1bb2c18) |

### 4. 수정 전후 비교

**철회 직후 같은 로그인으로 보낸 요청** (200 이용됨 · 201 저장됨 · 403 막힘)

| 요청 | 수정 전 | 수정 후 | 판단 |
|---|---|---|---|
| 내 정보, 토큰 재발급 | 200 | 200 | 계정·로그인 유지(의도) |
| 홈·건강기록·개인 챌린지·파티·캘린더 | 403 | 403 | 이미 차단 |
| 공통 챌린지 참여·인증 | **201** | **403** | 지운 기록을 다시 모으는 것이라 차단 |
| 커뮤니티·파이·캐릭터 | **200** | **403** | 약관과 불일치라 차단 |
| 동의 목록·다시 동의, 현재 약관, 내려받기 | 200 | 200 | 복귀 경로는 유지 |

### 5. 제약사항

- 철회해도 로그인(계정)은 유지돼요. 다시 동의하거나 내려받기·탈퇴를 하려면 필요해서 의도적으로 열어 뒀어요.
- 새 기능이 추가될 때 공통 동의 검사를 붙이지 않으면 다시 빠질 수 있어서, 묶음 전체에 자동 적용되는 구조와 회귀 시험으로 막았어요.

### 6. 재확인

- 막혀야 할 7곳은 403, 열려야 할 4곳은 200인 **회귀 시험**을 만들었어요.
- 철회 후 문의 답변 알림이 안 가는 시험도 추가했어요.
- **전체 시험 330개 통과.**

### 7. 남긴 근거

- 수정 PR #149 (b492f64 + 커뮤니티·파이·캐릭터 차단), 알림 확장(0b7f935, fde2e59)
- 회귀 시험 `test_consent_withdrawn_blocks_all.py`, `test_push.py`
- A안 되돌림 기록: 14c8632 → b018087

### 8. 배운 점

"시험이 모두 통과한다"는 시험이 다룬 경로가 안전하다는 뜻일 뿐이에요. 상태가 바뀌는 경로(철회 뒤 로그인 유지)를 시험 데이터로 직접 만들어 검사해야 빈틈이 드러나요. 이후 같은 묶음에 새 기능이 추가돼도 동의 검사가 자동으로 적용돼요.

## 사례 2. 모델 교체 후 과거 결과 보존

> 담당: 혜성(원칙·근거 문서, 모델), 혜림(서버 구현), 이슬(화면·안내)

---

### 슬라이드용 한 장

**제목:** 12주 도중 모델이 바뀌어도 한 사람의 전후 비교가 흔들리지 않게

| 항목 | 내용 |
|---|---|
| 문제 | 서버가 항상 최신 모델 하나로만 분석해서, 4주·12주 비교 때 **예전 입력값을 최신 모델로 다시 계산**하고 있었어요. 12주 중간에 모델이 바뀌면 같은 사람의 결과가 중간부터 새 모델로 나와요 |
| 선택 | 사람마다 **12주를 시작한 모델 버전으로 끝까지** 계산하고, 다음 12주는 새 버전으로 시작 |
| 선택한 이유 | 규제 문서는 "버전을 표시하고 알리라"는 용도라 고정을 요구하지 않아요. 고정은 **12주 전후 비교가 생활습관 변화를 보여 주려면 같은 모델이어야 해서** 팀이 고른 방식이에요. 영국 웰니스 의료 소프트웨어 회사의 환자별 고정 사례를 참고했어요 |
| 제약사항 | 모델 파일을 버전별로 읽어야 하고, 이전 12주와 새 12주는 모델이 달라 직접 비교할 수 없어요 |
| 수정 전 → 후 | 최신 모델로 재계산(비교 숫자가 바뀜) → 시작 버전으로 고정, 결과 화면에 버전 표시, 버전이 다르면 "모델이 업데이트되어 이번에는 비교하지 않아요" |
| 재확인 | 서버 구현 PR #200을 규칙 문서와 대조해 필드·오류 코드가 맞는지 확인(10/26) |

**한 줄 결론:** 모델 버전만 저장해서는 "당시 결과가 왜 그렇게 나왔는지" 설명이 보존되지 않아요. 사람별로 시작 버전을 고정하고 화면에 표시해야 전후 비교가 의미를 가져요.

---

### 1. 문제 발견

- 서버가 항상 최신 모델 하나로만 분석했어요.
- 그래서 4주·12주 비교 때 **예전 입력값을 최신 모델로 다시 계산**해 비교하고 있었어요.
- 12주 중간에 모델이 바뀌면 같은 사람의 결과가 중간부터 새 모델로 나오고, 전에 봤던 비교 숫자도 바뀌어요.
- 4차 멘토링의 "한 사람의 12주 안에서는 같은 모델로 비교, 중간 합류자는 따로"가 **절반만 지켜지고** 있었어요.

### 2. 판단 (선택한 이유)

- 모델 버전만 저장해서는 "당시 결과가 왜 그렇게 나왔는지" 설명이 보존되지 않아요.
- 식약처·FDA·IMDRF 가이드라인을 확인했어요. 규제 문서는 "언제, 누구에게 적용할지 미리 정하고, 버전을 표시하고, 알리라"는 용도예요. 모델을 반드시 고정하라는 기준은 없었어요.
- 사람별 버전 고정은 규제가 요구한 게 아니라, **12주 전후 비교가 생활습관 변화를 보여 주려면 같은 모델이어야 해서** 팀이 고른 방식이에요.
- 영국 웰니스 의료 소프트웨어 회사는 환자별로 고정해요. 12주 시작부터 끝까지 같은 버전으로 가고, 중간에 모델이 올라가도 그 환자는 그대로 가고, 새로 시작하는 환자는 새 버전으로 시작하며, 이전 버전 사용자 정보는 문서에 기록해요. 이 방식을 참고했어요.

### 3. 정한 원칙

1. 4주·12주 비교 모두 사람마다 **12주를 시작한 모델 버전으로 끝까지** 계산해요.
2. 결과 화면에 모델 버전을 표시하고, 버전이 바뀌면 배포 전에 안내해요.
3. 이 규칙을 변경 계획 문서에 미리 적어 둬요.
4. 과거 결과는 덮어쓰지 않고 버전과 함께 보존해요(이미 구현됨).
5. 다음 12주는 새 버전으로 시작하고, 이때도 사용자에게 안내해요.
6. 안전 문제나 버그가 생기면 고정과 상관없이 전원을 즉시 새 버전으로 바꾸고 안내해요.

### 4. 수정 전후 비교

| | 수정 전 | 수정 후 |
|---|---|---|
| 비교 계산 | 예전 입력값을 최신 모델로 재계산 | 12주를 시작한 모델 버전으로 끝까지 계산 |
| 과거 결과 | 비교 숫자가 바뀔 수 있음 | 덮어쓰지 않고 버전과 함께 보존 |
| 결과 화면 | 모델 버전 표시 없음 | 결과·12주 결과에 모델 버전과 업데이트 날짜 표시 |
| 버전이 다를 때 | 오류 또는 의미 없는 비교 | "모델이 업데이트되어 이번에는 비교하지 않아요" 안내 |
| 새 12주 | 12주를 마치면 끝 | 새 12주 시작 버튼, 새 버전 적용과 바뀐 점 안내 |

### 5. 구현 상태

| 날짜 | 내용 |
|---|---|
| 10/13 | 버전이 달라 비교할 수 없을 때 오류 없이 안내 문구 표시(이슬) |
| 10/22 | 4주 비교 응답에서 모델이 두 번씩 나오던 문제, 나이 고정 기준 수정(9dd18b2, 이슬) |

### 6. 제약사항

- 사람마다 다른 버전이 동시에 돌아서 **모델 파일을 버전별로 읽어야** 해요.
- 이전 12주와 새 12주는 모델이 달라 **직접 비교할 수 없어요.** 비교 화면은 만들지 않았고, 필요해지면 "모델이 달라 직접 비교할 수 없어요"를 보여 줄 계획이에요.
- 새 버전 배포 전 공지(무엇이 바뀌는지, 언제부터)는 관리자 공지 화면으로 올리고, 푸시로 보내려면 알림 종류를 추가해야 해서 담당 확정이 필요해요.

### 7. 재확인

- 서버 구현(PR #200)을 규칙 문서와 대조: `program_number`, `status` 필드, `restart`의 409 `PROGRAM_NOT_COMPLETE`, `review?program=N` 응답이 규칙과 같음을 확인했어요(10/26).
- 확인 항목: `cycle_number`가 프로그램 안에서 1~3인지, 12주를 안 마친 사람이 `restart`를 호출하면 409인지, restart 뒤 이전 12주의 결과·모델 버전이 그대로인지, `can_restart`가 마친 직후에만 true인지.
- 한계: 배포 후 실제 사용자 데이터로 12주가 끝까지 지난 사례는 아직 없어요(체험 기간이 4주 미만).

## 사례 3. 암호화와 복구

> 담당: 효민(서버·배포·구현·복구), 이슬(처리방침·동의 문구에 보호 범위 반영)

---

### 슬라이드용 한 장

**제목:** 이메일을 "잠근 값 + 찾기용 지문"으로 나눠 암호화하고, 복원까지 숫자로 확인

| 항목 | 내용 |
|---|---|
| 문제 | 건강 서비스인데 **이메일이 평문**으로, **서버 디스크는 암호화 없이** 저장돼 있었어요 |
| 선택 | 이메일을 **잠근 값(`email_enc`, Fernet)** 과 **찾기용 지문(`email_hash`, HMAC-SHA256)** 두 칸으로 나누고, 디스크·백업도 암호화 |
| 선택한 이유 | 이메일은 로그인 검색에 쓰여서 그냥 암호화하면 로그인이 깨져요(암호화한 값은 같은 이메일이라도 매번 다르게 저장돼 검색이 안 됨). 지문으로 찾고 원본은 잠가 두면 둘 다 해결돼요 |
| 제약사항 | 관리자 화면의 "이메일 일부로 검색"과 이메일 정렬을 포기, 건강 수치·설문 답은 칸 암호화를 하지 않음(디스크·백업 암호화로 보호), 키 교체 절차는 아직 없음 |
| 수정 전 → 후 | 이메일 평문·디스크 평문 → 이메일 암호화+지문, 디스크·백업 암호화 |
| 재확인 | 회원 20명 전원 로그인 성공(평문 0), 이메일 20개 원본과 동일(바뀐 것 0), 사진·암호화 값이 든 백업을 **3초 만에 복원해 표 49개 일치** |

**한 줄 결론:** 정보마다 민감도와 쓰임새를 보고 어느 층에서 잠글지 정했고, 잠근 뒤에도 쓸 수 있고 되돌릴 수 있는지를 숫자로 확인했어요.

---

### 1. 문제 발견

건강 서비스인데 **이메일이 평문**으로, **서버 디스크는 암호화 없이** 저장돼 있었어요.

### 2. 원인과 판단 (선택한 이유)

- EC2는 기본이 암호화가 아니에요.
- 이메일은 로그인 검색에 쓰여서 그냥 암호화하면 로그인이 깨져요. 암호화한 값은 같은 이메일이라도 매번 다르게 저장돼 검색이 안 돼요.
- 그래서 이메일을 **잠근 값(`email_enc`, Fernet)** 과 **비밀 키로 만든 찾기용 지문(`email_hash`, HMAC-SHA256)** 두 칸으로 나누고, 로그인·가입 중복 확인은 지문으로 찾기로 했어요.
- 대가로 관리자 화면의 "이메일 일부로 검색"과 이메일 정렬은 포기하고, 이메일 전체 또는 회원 번호로 찾게 바꿨어요.
- 정보마다 민감도와 쓰임새를 보고 어느 층에서 잠글지 정했어요(기준: 멘토님 답 10/13·10/20, 개인정보 보호법의 개인정보·민감정보 구분).

### 3. 수정

- 디스크를 암호화된 볼륨으로 바꿨어요(10/17).
- 이메일은 기존 회원 데이터를 **서비스를 멈추지 않고** 두 단계로 옮겼어요.
  - 1단계 PR #145: 새 칸을 채우고 옛 칸 비우기
  - 2단계 PR #159: 확인 뒤 옛 칸 지우기
- **키가 없거나 데이터가 이상하면 아무것도 바꾸기 전에 멈추게** 했어요.
- 배포 순서(서버에 키 두 개 먼저 → 사본 보관 → 백업 → 머지 → 검증)를 문서로 고정했어요.

**어느 층을 잠갔나 (네 층)**

| 층 | 조치 | 시점 |
|---|---|---|
| 통신 | HTTPS, HSTS(브라우저가 항상 HTTPS로만 접속) | 처음부터, HSTS 10/16 |
| 서버 디스크 | 암호화된 볼륨으로 교체(EC2는 기본이 암호화 아님), 옛 볼륨·스냅샷 삭제 | 10/17, 삭제 10/23 |
| 백업 | 서버 백업은 암호화된 디스크에, 맥북 사본은 AES-256으로 잠그고 비밀번호는 키체인에 | 10/12~ |
| 칸(컬럼) | 비밀번호는 해시, 보호자 이름·연락처와 이메일은 암호화 | 이메일 10/21 |

**정보마다 어떻게 정했나**

| 정보 | 결정 | 근거 |
|---|---|---|
| 비밀번호 | 해시(bcrypt) | 원래 값을 알 필요가 없어 되돌릴 수 없게 저장 |
| 이메일 | 암호화 + 찾기용 지문 | 사람을 바로 알아볼 수 있고 유출 피해가 큼. 로그인 때 찾아야 해서 지문을 따로 둠 |
| 건강 수치·설문 답 | 칸 암호화는 이번 범위 밖, 디스크·백업 암호화로 보호 | 예측 모델과 4주 비교가 매번 계산에 써서 칸마다 풀면 비용·위험이 큼. 멘토님도 "여유가 있으면"으로 정리 |
| 생년월일·성별 | 범위 밖 | 모델 입력이고 이메일 없이는 사람을 특정하기 어려움 |
| 접속 IP | 암호화하지 않고 3개월 뒤 삭제 | 법정 접속 기록이라 확인할 수 있어야 함 |

### 4. 수정 전후 비교

| | 수정 전 | 수정 후 |
|---|---|---|
| 이메일 | 평문 | 잠근 값 + 찾기용 지문 |
| 서버 디스크 | 암호화 없음 | 암호화된 볼륨(옛 볼륨·스냅샷 삭제) |
| 백업 | 암호화 없음 | 서버는 암호화된 디스크, 맥북 사본은 AES-256 |
| 관리자 이메일 표시 | 전체 표시 | 가린 이메일, "이메일 보기"를 누를 때만 전체 표시와 기록 |
| 관리자 검색 | 이메일 일부로 검색·정렬 | 이메일 전체 또는 회원 번호로 검색 |

### 5. 재확인 (잠근 뒤에도 쓰고 되돌릴 수 있는지)

| 확인 | 결과 |
|---|---|
| 로그인 | 회원 20명 전원 풀림·지문 일치, 평문 0 |
| 원본과 같은지 | 20명 모두 같음, 바뀐 것 0 (이메일은 출력하지 않고 지문만 비교) |
| 관리 업무 | 관리자 목록은 가린 이메일, "이메일 보기"를 누를 때만 전체 표시와 기록 확인 |
| 분석 | 예측 모델·4주 비교·운영 현황은 이메일을 쓰지 않아 영향 없음, 전체 자동 시험 통과 |
| 복원 | 새 백업을 임시 MySQL에 복원해 운영 DB와 비교 → 3초, 표 49개 행 수·사진 바이트 지문·암호화 이메일 지문·마이그레이션 번호 일치 |
| 디스크 | 교체 전후 계정 수·마이그레이션 번호·디스크 사용량 같음, 남은 디스크와 스냅샷 모두 암호화 |

**복원 시험에서 함께 알게 된 것**: 백업에는 커뮤니티 사진이 원래 바이트 그대로 들어 있어 글자로 읽는 첫 비교 스크립트가 사진 부분에서 멈췄고, 바이트로 읽도록 고쳤어요. 비교가 정말 차이를 잡는지 보려고 시험 환경에서 복원본의 사진 한 바이트를 일부러 바꿔 돌렸더니 바이트 수(18 → 19)와 지문이 달라진 것을 정확히 잡았어요. 복원한 이메일은 키가 있어야 읽혀서, 백업 파일만 새어 나가도 이메일은 드러나지 않아요.

**비밀값 없이 진행**: 키와 이메일은 화면·채팅·저장소에 나오지 않게 작업하고, 검사는 값 대신 형식·개수·지문으로 했어요.

### 6. 제약사항과 한계

- 건강 수치·설문 답은 칸 암호화를 하지 않았어요(디스크·백업 암호화와 접근 통제로 보호). 정식 서비스라면 다음 대상이에요.
- 관리자 기록의 관리자 이메일과 서버 설정의 관리자 목록은 평문이에요(관리자 본인 정보라 이번 범위에서 뺌).
- **키 교체 절차는 아직 없어요.** 키가 새면 모든 이메일을 새 키로 다시 잠그는 마이그레이션이 필요해요.
- 디스크 교체 때 서비스가 멈춘 시간은 재지 않았어요.
- 복원 시험은 체험 데이터 삭제(11/1까지) 뒤 새 스냅샷을 만들 때 한 번 더 돌릴 예정이에요.

### 7. 남긴 근거

- 민감도에 따른 선택 근거(위 표), 비밀값 없는 절차·검사 결과(위 표)
- 복원 시험 스크립트 `restore_check.sh`
- PR #145(1단계), #159(2단계)
- 이슬 몫: 처리방침에서 디스크 암호화를 "적용할 예정"에서 "완료(2026-10-17부터)"로 맞추고, 서버 접속·배포 인원을 구분하고, 이메일 컬럼 암호화·관리자 화면 마스킹, 보관·삭제 기간 표를 문서와 화면에 정확히 반영했어요. 확인하지 못한 것(건강정보 전체 암호화 여부 등)은 쓰지 않았어요.
