# API 권한·보안 검사 결과 (2026-10-29)

> 멘토링 10/20·10/26: AI로 코드 리뷰·권한 검토를 돌려 수정할 곳을 찾고, 크리티컬한 것만 발표 자료로 쓰기.
> 대상: 서버(`repo-be`, `yiseul_2`) 경로 141개(검사 시점, `/predict` 삭제 후 140개)와 화면(`frontend`). 코드 검사 + 로컬 서버 실제 요청 시험.
> 앞서 효민님이 4묶음으로 한 검사(요청 크기 제한, 보안 헤더, 앱 파일 숨김 등)는 반영돼 있는 것을 확인했고, 이번에는 권한과 남용 쪽을 중심으로 다시 봤어요.

## 한 줄 결론
**크리티컬(바로 뚫리는 곳)은 없어요.** 인증·관리자 권한·남의 자료 접근은 모두 막혀 있고, 고칠 것은 낮은 위험 3건이에요.

## 고칠 것 (낮은 위험 3건) — 3건 모두 수정 완료 (2026-10-29)

운영 서버에서 `/docs`·`/openapi.json`·`/v1/predict`가 404, 가입 제한이 429로 동작하는 것을 효민님이 확인했어요. 경로는 140개, 로그인 없이 열리는 경로는 7개로 바뀌었어요.

### 1. 가입 횟수 제한이 없어요 — 중간~낮음 → **수정 완료**(IP당 1시간 20회, 429)
- **시험**: 같은 IP에서 가입을 15번 연속 보내니 **15번 모두 성공(201)**.
- **위험**: 가짜 계정을 대량으로 만들어 DB를 채우거나 서비스 자원을 쓸 수 있어요. 또 이미 가입된 이메일이면 409를 돌려줘서, 횟수 제한이 없으면 "이 이메일이 가입돼 있나"를 계속 물어볼 수 있어요.
- **고치는 방법**: 로그인 실패 제한(`login_guard`)과 같은 방식으로 IP당 가입 횟수를 제한해요(예: 1시간 10건). 로그인 제한이 이미 있어서 같은 구조를 재사용하면 돼요.
- **담당 후보**: 혜림(인증 서버).

### 2. 운영 서버에서 API 문서가 공개돼 있어요 — 낮음 → **수정 완료**(`/docs`·`/openapi.json` 404, 효민)
- `/docs`와 `/openapi.json`이 로그인 없이 열려요(200). 경로 117개와 요청 모양 전체가 보여서, 공격 연습 지도를 주는 셈이에요.
- 인증이 뚫리는 건 아니에요. 고치는 방법: 운영에서는 문서를 끄거나(`docs_url=None`) Caddy에서 막기.
- **담당 후보**: 효민(배포 설정).

### 3. 예측 임시 창구(`/predict`)가 남아 있어요 — 낮음 → **수정 완료**(404 확인)
- "모델 연결 확인용 임시"로 만든 경로가 운영에 남아 있어요. 로그인은 필요하고 화면에서도 쓰지 않아요.
- 정식 흐름(`/health/records` → `/predictions/jobs`)이 있으니 지우는 게 맞아요. 남아 있으면 로그인한 회원 누구나 모델 계산을 무제한 호출할 수 있어요.
- **담당 후보**: 혜림 또는 혜성(예측).

## 서버 접속·포트 확인 (2026-10-29, 서버 안에서 직접 확인)

효민님이 운영 서버(EC2)에서 명령을 실행해 확인한 결과예요.

| 확인 | 결과 | 판단 |
|---|---|---|
| 밖에서 받는 포트 | **22, 80, 443만** (IPv4·IPv6 모두) | 통과. 8000(API)·3306(DB)은 서버 안에서만 열려 있음 |
| SSH 비밀번호 로그인 | `passwordauthentication no` | 통과. 비밀번호를 맞히는 공격이 불가능 |
| SSH 열쇠 인증 | `pubkeyauthentication yes` | 통과 |
| root 로그인 | `permitrootlogin prohibit-password` | 통과. root는 열쇠로만 가능 |
| 로그인 가능한 계정 | root, ubuntu (2개) | 보통. 쓰지 않으면 root 로그인을 아예 막는 것이 더 안전 |
| 등록된 SSH 키 수 | 1개 | 효민님 맥북과 GitHub Actions 자동 배포가 **같은 키**를 씀. 팀원이 공유하는 건 아니지만 **사람 접속과 배포 접속을 구분할 수 없음**(한계) |

- 위 결과로 "밖에 열린 문은 22·80·443만"이라는 결과보고서 34장 문장이 사실임을 확인했어요.
- **AWS 보안 그룹(콘솔 확인, 효민)**: 인바운드 규칙이 22·80·443 세 개뿐이고 서버 안에서 본 결과와 같아요. 22번(SSH)의 원본은 `0.0.0.0/0`(모든 IPv4)이에요. 자동 배포(GitHub Actions)가 매번 다른 주소에서 SSH로 들어와서 특정 IP로 좁히지 않았고, 대신 비밀번호 로그인을 끄고 열쇠로만 들어오게 해서 막고 있어요.
- **남은 한계**: 22번이 전 세계에 열려 있어서, 열쇠가 새면 바로 접속할 수 있어요. 열쇠 인증만 허용하는 것이 방어선이에요.
- **다음 단계(정식 운영이라면)**: 22번을 아예 닫고 AWS 세션 매니저로 접속하면 열린 SSH 포트 없이 사람별 접속 기록(CloudTrail)을 남길 수 있어요. 배포는 GitHub Actions의 IP 목록으로 좁히거나 배포 전용 키로 나누는 방법이 있어요.
- **SSH 키 1개의 정체(효민님 확인)**: 팀원이 공유하는 키가 아니라 효민님 맥북과 GitHub Actions 자동 배포가 같이 쓰는 키예요. 그래서 한계는 "사람이 접속한 것과 배포가 접속한 것을 구분할 수 없다"예요. 배포용 키를 따로 만들면 풀려요.
- **멘토 권고와 연결(10/20, 멤버별 IAM)**: IAM은 AWS 콘솔 계정이라 SSH 키와 별개예요. 팀원별 IAM 계정은 10/23에 이미 만들었고, 남은 일은 4명의 권한을 **최소 권한**으로 줄이는 거예요.
- 열쇠 내용과 서버 비밀 값은 캡처·보고서에 넣지 않았어요(포트, 계정 이름, 설정 값, 키 개수만 기록).
