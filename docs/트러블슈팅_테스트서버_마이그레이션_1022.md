# 테스트 서버 500 오류: 코드가 DB보다 뒤처진 마이그레이션 불일치 (2026-10-22)

**한 줄 요약**: 이미 최신 마이그레이션(#159, 옛 평문 `users.email` 칸 삭제)까지 올라간 테스트 DB에, 그 변경이 없는 옛 브랜치 코드를 올려서 코드가 없는 칸을 찾다 500이 났다. 브랜치에 최신 main을 합치고 테스트 DB를 새로 만들어 해결했다.

## 1. 문제 정의

- **언제·어디서**: 2026-10-22, 팀원 사전 체험용 **테스트 서버**(효민 맥북, 별도 compose 프로젝트 `paeon-demo`, 지인용 운영 서버와 DB·주소 모두 분리). 운영 서버에는 영향 없음.
- **증상**: 로그인, 문의 목록, 4주 재입력 화면(`GET /v1/challenges/cycles/{id}/review`) 등 **회원 정보를 읽는 기능이 모두 500**.
- **로그**:
  - `sqlalchemy.exc.OperationalError: (asyncmy.errors.OperationalError) (1054, "Unknown column 'users.email' in 'field list'")`
  - `alembic`: `Can't locate revision identified by '1a9a51da1d1a'`

## 2. 원인 분석

일어난 순서:

| 순서 | 테스트 서버 코드 | DB 마이그레이션 단계 | 결과 |
| --- | --- | --- | --- |
| 1 | `main`(f438683, #159 포함)으로 처음 띄우고 `alembic upgrade head` | `1a9a51da1d1a`까지 올라감 → **`users.email` 칸이 삭제됨** | 정상 |
| 2 | 팀 요청으로 코드를 `feature/demo-day-offset`(a9161c0)로 바꿈 | 그대로 `1a9a51da1d1a` | — |
| 3 | 이 브랜치는 **#159보다 먼저 갈라져서**, User 모델이 아직 옛 `users.email` 칸을 읽고 `1a9a51da1d1a` 마이그레이션 파일도 없음 | 칸은 없는데 코드가 찾음 | **1054 → 500**, alembic은 DB에 적힌 번호를 코드에서 못 찾음 |

- 확인: `git merge-base --is-ancestor 287fba7 origin/feature/demo-day-offset` → 당시 브랜치에 #159(287fba7)가 **없었음**.
- **자동 시험으로는 잡히지 않은 이유**: 시험은 매번 그 코드의 모델로 새 DB(SQLite)를 만들어서 코드와 DB가 항상 같은 단계다. 같은 코드(a9161c0)로 4명 체험 흐름과 4주 재입력 화면을 재현했을 때도 200이었다. 이 오류는 **이미 앞서간 DB에 뒤처진 코드를 올릴 때만** 생긴다.

## 3. 시도했다가 되돌린 것

- **`alembic stamp 3583058d4b4f`(DB에 적힌 번호만 강제로 바꾸기)**: DB 구조는 그대로 두고 기록만 바꾸므로, `users.email` 칸이 없는 문제는 그대로다. 오히려 기록과 실제 구조가 어긋나서, 나중에 main을 올리면 이미 없는 칸을 또 지우려다 실패하는 식의 더 큰 문제를 만든다. 팀원 피드백을 받고 쓰지 않기로 했다.
- **명령 실행 실수**: 붙여 넣은 명령의 따옴표·특수문자가 깨지고, 홈 폴더에서 git 명령을 실행해 실패했다.

## 4. 수정

1. **코드를 DB와 같은 단계로**: `feature/demo-day-offset`에 최신 `main`을 합쳐(merge) #159의 모델 변경과 마이그레이션 파일이 들어오게 했다.
2. **테스트 서버만 초기화**: 테스트 계정뿐이라 데이터를 지워도 되는 서버라서, 볼륨까지 지우고 새로 만들었다.
   ```bash
   git pull origin feature/demo-day-offset
   docker compose down -v
   docker compose up -d --build
   docker compose exec fastapi alembic upgrade head
   ```
   (팀원 가입 계정은 다시 만들어야 했다.)

## 5. 재확인

- [ ] `docker compose exec -T fastapi alembic current`가 `alembic heads`와 같은 번호(`… (head)`)
- [ ] 로그인 성공
- [ ] 문의 목록 열림
- [ ] 4주 재입력 화면(`/review`) 200
- [ ] fastapi 로그에 `Unknown column`·`Can't locate revision` 없음: `docker compose logs fastapi --since 10m | grep -ciE "unknown column|can't locate"` → `0`

## 6. 다음부터 지킬 것

1. **이미 쓰던 DB에서 코드(브랜치)를 바꾸기 전에** DB 단계와 코드 단계를 비교한다.
   ```bash
   docker compose exec -T fastapi alembic current   # DB가 어디까지 왔나
   docker compose exec -T fastapi alembic heads     # 이 코드가 아는 마지막 단계
   ```
   `alembic current`가 `Can't locate revision`으로 실패하면 **코드가 DB보다 뒤처진 것**이다. 그 브랜치에 main을 먼저 합친다.
2. 테스트 서버에 올릴 브랜치는 **최신 main을 합친 뒤** 올린다. 특히 마이그레이션이 들어간 PR(#145, #159처럼)이 머지된 직후에는 꼭.
3. `alembic stamp`는 **DB 구조가 그 번호와 정말 같을 때만** 쓴다. 오류를 없애려고 번호만 바꾸지 않는다.
4. `docker compose down -v`(볼륨까지 삭제)는 **테스트 서버에서만**. 운영 서버는 `backup.sh`와 롤백 절차(배포 노트 §6)를 따른다.
5. 명령은 **프로젝트 폴더에서**, 어느 터미널(서버/맥북)인지 확인하고 실행한다. 긴 명령은 파일로 만들어 실행한다(배포 노트 §5).

## 7. 포트폴리오용 정리

- **문제**: 팀 사전 체험 서버에서 로그인·4주 재입력 등 회원 정보를 읽는 기능이 모두 500.
- **원인**: DB는 #159 마이그레이션으로 `users.email` 칸이 지워진 상태였는데, 그 변경 전에 갈라진 브랜치 코드를 올려서 코드가 없는 칸을 조회함. 자동 시험은 매번 새 DB를 만들어 이 불일치를 잡지 못함.
- **수정**: 기록만 바꾸는 `alembic stamp` 대신, 브랜치에 최신 main을 합쳐 코드와 DB를 같은 단계로 맞추고 테스트 DB를 새로 만듦.
- **재확인**: `alembic current`와 `heads` 일치, 로그인·문의 목록·4주 재입력 화면 정상. 이후 브랜치를 바꾸기 전에 두 번호를 비교하는 절차를 배포 노트에 추가.
