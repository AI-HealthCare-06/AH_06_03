# 멘토링 피드백으로 서비스를 고친 과정: PAEON 프론트엔드·커뮤니티 개발기

> 초안입니다. `[확인]` 표시는 본인이 숫자·사실을 채우거나 확인해야 하는 곳이에요.

## 프로젝트 한 줄 소개

PAEON은 생활 습관 정보로 10년 내 심혈관 위험 신호를 예측하고, 4주 챌린지로 습관을 바꾸도록 돕는 건강 관리 웹 서비스예요. (팀 4명, 모바일 웹) 저는 프론트엔드 전체와 커뮤니티·관리자 기능 일부, 약관·처리방침 문구 맞춤을 맡았어요.

- 스택: 정적 HTML/JS(모바일 390px), FastAPI, SQLAlchemy, Alembic, MySQL
- 역할: 프론트엔드, 커뮤니티·파티 피드·사진 업로드·관리자 API 일부, 법적 문구 정리

---

## 위기 1. 멘토링에서 "좁고, 쓰는 법이 헷갈리고, 동기가 안 보인다"는 평가를 받았다

### 상황
멘토링에서 화면이 좁고 모바일 최적화가 부족하며, 챌린지 화면은 어떻게 쓰는지 헷갈리고 보상 체계가 안 보인다는 지적을 받았어요. 앱 대신 모바일 웹으로 가라는 조언도 함께 받았어요.

### 원인 분석
- 데스크톱 기준 레이아웃에 사이드 메뉴가 남아 있었고, 화면마다 색·간격·버튼 모양이 달랐어요.
- 챌린지의 핵심 규칙(14일 중 10일 인증하면 완주, 순위는 인증한 일수로 결정)이 작은 회색 글씨로 묻혀 있었어요.
- 설명글이 길어서 정작 필요한 정보가 눈에 안 들어왔어요.

### 해결
- 디자인 시안(파랑+크림, 나눔고딕, 390px)을 만들고, 공통 스타일과 하단 탭 5개로 구조를 바꿨어요.
- 시안 49화면 `[확인]`을 실제 화면으로 옮기고, 화면마다 시안과 나란히 비교해서 차이를 하나씩 고쳤어요.
- 문구 원칙을 정했어요. 설명은 한 줄로 줄이고, 완주 조건·순위 기준·인원 제한 같은 핵심 규칙은 크게 보여 줘요. 법적 문구와 동의 문구는 길어도 손대지 않아요.
- 동기 부여를 위해 파이(포인트), 배지 진행도(피자 조각처럼 채워지는 링), 캐릭터 꾸미기, 파티 챌린지를 화면에 연결했어요.

### 결과
- 하단 탭, 상단 바, 공통 컴포넌트가 하나로 통일됐어요.
- 챌린지 화면에서 완주 조건과 순위 기준이 한눈에 보여요.

## 위기 2. 법적 표현과 개인정보: 한 단어가 서비스의 성격을 바꾼다

### 상황
멘토링에서 "진단" 대신 "예측·분석", "위험도" 대신 "위험 신호"로 쓰라는 점, 12주 결과로 "건강이 좋아졌다"고 결론 내리면 의료기기 문제가 될 수 있다는 점을 들었어요.

### 원인 분석
- 서비스 곳곳에 "진단", "걱정되면 병원에" 같은 표현이 흩어져 있었어요.
- 약관·처리방침 문구와 서버가 저장하는 동의 문구가 따로 놀면 동의 기록이 어긋날 수 있어요.

### 해결
- 모든 화면의 면책 문구를 한 문장으로 통일했어요. "진단이 아닌 참고 정보입니다. 정확한 판단은 의료진과 상담하세요."
- 법적 문구는 사용자가 명시적으로 요청한 경우에만 바꾸는 규칙을 세웠어요.
- 약관 v4 문구를 서버 마이그레이션과 맞춰서, 서버 PR이 먼저 배포된 뒤 화면 PR을 올리도록 순서를 지켰어요.
- 건강정보 동의 철회 시 지우는 테이블 목록(`HEALTH_KEEP_TABLES`)을 팀과 공유해서, 철회 범위를 코드와 문구가 일치하게 했어요.

### 결과
- 화면·약관·서버 동의 기록이 같은 문구를 가리켜요.

## 위기 3. 사진을 올리게 하면 위치 정보가 같이 올라간다

### 상황
커뮤니티 글에 사진을 붙이는 기능을 만들 때, 스마트폰 사진에는 촬영 위치(EXIF GPS)가 들어 있어서 그대로 올리면 집 위치가 노출될 수 있었어요.

### 원인 분석
- 화면에서 막아도 API를 직접 호출하면 우회돼요. 한 곳만 막는 건 불충분했어요.

### 해결
- 화면: 사진을 캔버스에 다시 그려 JPEG로 재인코딩하면서 EXIF를 제거하고, 300KB 이하로 줄여서 올려요. `[확인]` 3.9MB 원본이 300KB 이하로 줄어드는 것을 확인했어요.
- 서버: JPEG 여부, 크기(300KB), 장수(3장), EXIF의 GPS 항목을 직접 검사해서 위반하면 각각 415·413·409·400으로 거절해요.
- 글 작성 후 사진 업로드가 실패하면 글도 함께 삭제해서, 사진 없이 글만 남는 상태를 막았어요.
- 파티가 해산되면 파티 글·사진·좋아요·댓글·신고가 함께 삭제되도록 연쇄 삭제를 걸었어요.

### 결과
- 서버 테스트 190개 통과 `[확인]`, 업로드부터 조회까지 e2e로 확인했어요.

## 위기 4. 마이그레이션 순서와 배포 의존성

### 상황
프론트가 서버 API에 의존하는데, 서버 PR이 머지·배포되기 전에 프론트를 올리면 화면이 깨져요. 마이그레이션 체인도 여러 사람이 이어 붙이고 있었어요.

### 해결
- 서버 PR → 배포 → 프론트 PR 순서를 PR 설명에 명시했어요.
- 새 컬럼이 들어가는 변경은 Docker MySQL에서 up/down을 모두 돌려서 확인한 뒤 올렸어요.
- 효민님의 신고 자동 숨김·단계 제재 계획과 제 계정 정지 기능이 겹치는 걸 발견해서, 겹치는 파일 목록을 공유하고 머지 순서를 정리했어요.

### 결과
- 서버(#109)와 프론트(#110)가 충돌 없이 순서대로 머지됐어요.

## 위기 5. 직접 겪은 실수와 재발 방지

- 문자열 치환 중 문법 오류가 난 파일을 푸시했다가 바로 고친 적이 있어요. 그 뒤로 수정한 인라인 스크립트는 `node --check`로 검사한 뒤 푸시해요.
- 관리자 화면은 공통 스크립트를 불러오지 않는데 공통 함수를 썼다가 오류가 났어요. 화면별 의존성을 확인하고, 관리자 화면은 기본 `confirm()`을 쓰도록 되돌렸어요.
- SQLite "database is locked": 쓰기를 열어 둔 채 API를 호출한 게 원인이었어요. DB 쓰기는 즉시 커밋하고 API 호출과 분리했어요.
- 테스트 계정 정보가 개발 서버를 재시작하면 사라지는 문제는 `KEEP_DB` 옵션과 시드 스크립트로 해결했어요.

---

## 배운 점

1. 멘토링 피드백은 "문제 정의 → 원인 분석 → 수정 → 재확인" 순서로 기록하면 그대로 포트폴리오가 돼요.
2. 같은 기준을 한 곳에서만 막으면 우회돼요. 사진 위치 정보처럼 화면과 서버 양쪽에서 확인해야 해요.
3. 서버와 화면이 맞물리는 작업은 코드보다 배포 순서가 더 큰 위험이에요.
4. 법적 문구는 개발자가 마음대로 다듬지 않고, 바꿀 때는 근거와 승인을 남겨요.

## 이력서용 한 줄 요약 (골라 쓰세요)

- 멘토링 피드백(모바일 최적화·UX 불명확)을 반영해 49화면 `[확인]` 리디자인을 적용하고, 공통 컴포넌트·하단 탭으로 화면 구조를 통일
- 사진 업로드의 위치정보 노출 문제를 클라이언트 재인코딩(EXIF 제거·300KB)과 서버 검증(JPEG·크기·GPS 태그)의 이중 방어로 해결
- 커뮤니티·파티 피드·배지 진행도·관리자(공통 챌린지 수정·삭제, 신고 처리, 회원 정지·삭제) 기능을 설계·구현하고 서버 테스트 190개 통과 `[확인]`
- 서버·프론트 의존 배포 순서와 마이그레이션 체인을 관리하고, MySQL에서 up/down을 검증해 무중단에 가깝게 배포
- 개인정보·의료 표현 가이드(진단→예측/위험 신호)를 전 화면과 약관 문구에 일관되게 적용
